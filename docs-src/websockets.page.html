A route file can accept a WebSocket connection, exchange messages with the browser, and be pushed to from anywhere else in your server. WebSocket support is built on Node's own crypto and socket primitives, so it adds no dependencies.

This is the transport layer. It gives you a connection and messages on it. Channels, topics, presence, rooms and mapping a socket to a signed-in user are all things you build on top — see What is not included.

There is a live demo you can open while running npm run dev in this repo.

Your First Socket Route

Create a WS.js file. It sits alongside GET.js and POST.js, and exports a default function like any other route file:

// chat/WS.js
export default async (request, socket) => {
  socket.on('message', (data, isBinary) => {
    socket.send(`echo: ${data}`);
  });
};

The URL is the directory, exactly as it is for HTTP routes — this route answers a handshake at /chat. Connect to it with the browser's built-in WebSocket:

const socket = new WebSocket(`ws://${location.host}/chat`);

socket.addEventListener('open', () => socket.send('hello'));
socket.addEventListener('message', (event) => console.log(event.data));

The same URL can serve a page and a socket at once. A GET.page.html next to WS.js is served to a normal browser navigation, while a handshake at that path opens the socket, because the two arrive as different kinds of request.

How a Handshake Is Routed

Upgrades use the same file-based rules as HTTP routes, with one deliberate restriction.

  • Only a file named exactly WS.js is ever run for an upgrade. Directory requests normally fall back to index.js and then CATCH.js; upgrades do not. A handshake at a path with no WS.js gets 404 and the connection closes, even if that path has a working GET.js.
  • Dynamic segments work. room/[id]/WS.js answers /room/abc with request.params.id set to "abc".
  • A normal HTTP request never executes WS.js. It is a route file, so it is never served as source either.
  • Custom and wildcard routes work. A WS.js in a directory mapped in through customRoutes answers an upgrade the way it would answer an HTTP request, in the same order: an exact custom route, then a wildcard route, then the served tree. This is how a package in node_modules can ship a socket route. A path containing a .. segment is refused outright, since a mapped directory can sit outside the root.

An open connection keeps the copy of WS.js it started with. Editing the file only affects connections opened afterwards, so reconnect (or restart) to pick up a change.

The Socket Object

The second argument is the connection. The first is the same enhanced request object an HTTP route receives, so request.headers, request.cookies, request.query, request.params and request.path all behave identically. There is no body on an upgrade, so request.body is null.

Properties

  • socket.path — the URL path this connection was opened on
  • socket.params, socket.query, socket.headers, socket.cookies — copies of the handshake values
  • socket.data — an empty object for your own use. Whatever you put here is what you select on when pushing from outside the route.
  • socket.readyState — "connecting", "open", "closing" or "closed"

Methods

  • socket.send(data) — sends a string as text, a Buffer or Uint8Array as binary, and anything else as JSON. Returns false if the connection can no longer accept data; it never throws.
  • socket.close(code, reason) — starts a clean closing handshake. Defaults to 1000.
  • socket.terminate() — drops the connection immediately, with no closing handshake.
  • socket.ping(payload) — sends a ping. The heartbeat does this for you.
  • socket.reject(status, message) — refuses the upgrade. Only valid before the connection opens; see below.
  • socket.on(event, handler) / socket.off(event, handler)

Events

  • message — (data, isBinary). Text arrives as a string, binary as a Buffer. Fragmented messages are reassembled before this fires, so you always get whole messages.
  • close — (code, reason). The code is 1006 when the connection dropped without a close frame, for instance a closed tab or a lost network.
  • error — (error)
  • open — fires once the handshake has completed
  • ping / pong — (payload). Pings are answered automatically; these are informational.

A handler that throws closes its own connection with 1011 and logs the error. Other connections are unaffected and the process stays up. This covers async handlers too.

Authenticating a Connection

Your route runs before the handshake completes, which is what lets it refuse one. Call socket.reject(status) and the client gets an ordinary HTTP error — no socket is ever established:

// account/WS.js
import getSession from '../../server/utils/auth/getSession.js';

export default async (request, socket) => {
  const [error, session] = await getSession({ token: request.cookies.session_token });

  if(error) return socket.reject(401, 'Unauthorized');

  socket.data.userId = session.userId;

  socket.on('message', (data) => {
    socket.send(`hello user ${socket.data.userId}`);
  });
};

Because this is the same cookie parsing HTTP routes use, session auth needs no WebSocket-specific code. Sends made before the handshake finishes are queued and flushed as soon as it does, so you can send() straight away.

Pushing From Outside the Route

Any server code can reach connected sockets — an HTTP route, a webhook handler, a kempo (CMS) extension:

// notify/POST.js
import { sockets, broadcast } from 'kempo-server/websocket';

export default async (request, response) => {
  // Every connection on one route path
  const listeners = sockets({ path: '/account' });

  // Filtered by whatever the route attached to socket.data
  const sent = broadcast({ type: 'order.paid', id: request.body.orderId }, {
    path: '/account',
    filter: (socket) => socket.data.userId === request.body.userId
  });

  response.json({ delivered: sent });
};
  • sockets({ path, filter }) — returns matching connections. Both options are optional; with neither, you get every open socket.
  • broadcast(message, { path, filter }) — sends to every match and returns how many received it.
  • closeAll(code, reason) — closes every open socket.

This is single-process only. The registry lives in the process that accepted the connection. Behind a load balancer, or with more than one worker, a socket is only reachable from its own process — pushing from another one will silently match nothing. Anything that needs cross-process fan-out needs a shared bus (Redis, a message queue) above this layer.

Configuration

All WebSocket options live under websocket in your config file, and all of them have working defaults:

{
  "websocket": {
    "enabled": true,
    "maxMessageSize": 1048576,
    "allowedOrigins": null,
    "requireOrigin": false,
    "heartbeatInterval": 30000,
    "heartbeatTimeout": 10000
  }
}
  • enabled — set false to refuse every upgrade with a 404. Default true.
  • maxMessageSize — largest message accepted, in bytes. Default 1MB.
  • allowedOrigins — null for same-origin only, "*" for any origin, or an array of exact origins.
  • requireOrigin — reject a handshake that sends no Origin header at all. Default false.
  • heartbeatInterval — how often an idle connection is pinged, in milliseconds. 0 disables the heartbeat.
  • heartbeatTimeout — how long to wait for the answering pong before dropping the connection.

Origin Checking

By default a handshake is only accepted from the origin the server was reached on. This matters more than it might look.

Cookies are sent on a WebSocket handshake, and browsers apply no same-origin policy to WebSockets — there is no preflight and nothing is blocked client-side. Without a server-side check, any page on any site could open a socket to your server that is fully authenticated as whoever is signed in. That attack is called cross-site WebSocket hijacking, and this check is the only thing standing in its way.

To allow specific other origins, list them exactly:

{
  "websocket": {
    "allowedOrigins": ["https://app.example.com", "https://admin.example.com"]
  }
}

A handshake with no Origin header is allowed by default. Browsers always send one, so its absence means a non-browser client — a CLI tool, a service, another server — which carries no ambient cookies and is not what this check defends against. Set requireOrigin: true to turn those away as well.

Limits and Liveness

A message larger than maxMessageSize closes the connection with 1009. The limit is checked against the size a frame declares, before any of its payload is buffered, so an oversized claim costs nothing, and it is enforced again on the reassembled total so a peer cannot walk past it with many small fragments. Note that this is a separate setting from maxBodySize, which bounds HTTP request bodies and defaults far higher.

Idle connections are pinged every heartbeatInterval and dropped if no pong comes back within heartbeatTimeout. This is what notices a client that vanished without closing — a closed laptop, a dropped network — which TCP alone can leave looking open indefinitely. Connections with traffic on them are not pinged; traffic is its own proof of life.

When the server shuts down, including on Ctrl-C, open sockets are sent close 1001 so a browser can reconnect immediately rather than waiting on a dead connection.

Middleware

Your configured middleware chain runs for the handshake: CORS, rate limiting, security headers, request logging and any custom middleware. A middleware that ends the response rejects the upgrade, and its status and body reach the client. Headers it sets are carried onto the 101 response.

Compression middleware is skipped for upgrades. A 101 has no body to compress, and compression works by wrapping the response write path, which an upgrade never uses.

What Is Not Included

This is deliberately a transport. It does not provide:

  • Channels, topics, rooms or presence. socket.data plus a filter is the primitive you build these from.
  • Cross-process fan-out. The registry is per-process, as described above.
  • Automatic reconnection. Browsers do not reconnect a closed WebSocket; add that in your client code.
  • permessage-deflate or any other WebSocket protocol extension. Messages travel uncompressed.
  • Subprotocol negotiation. Sec-WebSocket-Protocol is not negotiated.

Complete Example

A route that tracks who is connected and lets an HTTP endpoint push to one of them.

// feed/WS.js
export default async (request, socket) => {
  const room = request.query.room;
  if(!room) return socket.reject(400, 'A room is required');

  socket.data.room = room;
  socket.send({ type: 'joined', room });

  socket.on('message', (data) => {
    socket.send({ type: 'ack', received: data });
  });

  socket.on('close', (code) => {
    console.log(`left ${room} (${code})`);
  });
};
// feed/announce/POST.js
import { broadcast } from 'kempo-server/websocket';

export default async (request, response) => {
  const { room, text } = request.body;

  const delivered = broadcast({ type: 'announcement', text }, {
    path: '/feed',
    filter: (socket) => socket.data.room === room
  });

  response.json({ delivered });
};
// The browser side
const socket = new WebSocket(`ws://${location.host}/feed?room=general`);

socket.addEventListener('message', (event) => {
  const message = JSON.parse(event.data);
  console.log(message.type, message);
});

socket.addEventListener('close', (event) => {
  // 1001 means the server is restarting, so reconnecting shortly is worthwhile
  if(event.code === 1001) setTimeout(connect, 1000);
});
